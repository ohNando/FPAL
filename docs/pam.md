# pam_fpal

`pam_fpal.so` adds fingerprint verification to every program that uses PAM (sudo, su, login, GDM).

```
auth  sufficient  pam_fpal.so  [timeout=ms] [retries=n] [debug] [quiet]
```

| Option | Default | Meaning |
|---|---|---|
| `timeout=` | 10000 | How long to wait for a finger on each attempt (ms) |
| `retries=` | 3 | How many times to retry after a wrong finger (at most 10) |
| `debug` | off | Write verbose messages to the auth log |
| `quiet` | off | Hide the prompt and result messages |

Messages are shown even when the `PAM_SILENT` flag is set: sudo sends it by default, and without a prompt the user cannot tell that a finger is expected. Use `quiet` to turn the messages off.

| Situation | Message shown |
|---|---|
| Before each attempt | `[sudo] fingerprint for ohnando:` (service name and user; format set by `FPAL_PAM_PROMPT_FMT`) |
| Wrong finger, attempts left | `Fingerprint not recognised, try again` |
| Last attempt also wrong | `Fingerprint not recognised` |
| Timed out | `No finger detected` |

## Return values

| Situation | Return |
|---|---|
| Finger matched and the ID is bound to the user | `PAM_SUCCESS` |
| Wrong finger on every attempt | `PAM_AUTH_ERR` |
| No binding, sensor missing or busy, remote session (`PAM_RHOST`), timeout | `PAM_AUTHINFO_UNAVAIL` |

If the user has no binding the sensor is never opened and the stack falls through to the password immediately. The module should be used as `sufficient`, so the password always works when the fingerprint does not.

## Trying it safely

While editing PAM files, **keep a root shell open in a separate terminal with `sudo -i`**. If something goes wrong you can undo it from there.

1. Bind your finger to your user first:

   ```sh
   sudo ./build/fpal bind $USER
   ```

2. Create a test service that leaves the rest of the system alone. The module is loaded straight from `build/`, without installing it:

   ```sh
   printf 'auth     sufficient %s/build/pam_fpal.so debug\nauth     required   pam_deny.so\naccount  required   pam_permit.so\n' \
       "$PWD" | sudo tee /etc/pam.d/fpal-test
   sudo pamtester fpal-test $USER authenticate
   ```

   A bound finger should give `successfully authenticated`, any other finger `Authentication failure`.

3. Logs:

   ```sh
   sudo journalctl -b --no-pager | grep pam_fpal
   ```

4. Remove the test service: `sudo rm /etc/pam.d/fpal-test`

## sudo and su (Fedora / authselect)

`/etc/pam.d/system-auth` is generated by authselect, and manual edits are overwritten on the next update. For that reason a `custom/fpal` profile derived from `local` is used. In this profile only the `pam_fprintd.so` lines become `pam_fpal.so`:

```sh
sudo make install                         # /usr/local/sbin/fpal + /usr/lib64/security/pam_fpal.so
sudo fpal setup                           # select the profile, mask fprintd
```

`fpal setup` runs `platform.sh` (installed next to `fpal`) with the `authselect` backend. It backs up the previous settings (`authselect backup-list`). It also masks `fprintd`; otherwise fprintd could grab the sensor and keep pam_fpal from opening it.

Then try it in a new terminal with `sudo -k; sudo true`. If no finger is presented, the password is asked after 10 seconds.

To undo it:

```sh
sudo fpal setup --revert
```

## sudo and su (Debian / Ubuntu)

Debian generates `/etc/pam.d/common-auth` from small profile files in `/usr/share/pam-configs/`. fpal ships one called `fpal` (not enabled by default), and `fpal setup` enables it with `pam-auth-update`:

```sh
sudo make install PREFIX=/usr PAMDIR=/usr/lib/$(gcc -dumpmachine)/security \
    PAMCONFIGDIR=/usr/share/pam-configs
sudo fpal setup                           # pam-auth-update --enable fpal, mask fprintd
```

The profile adds `auth [success=2 default=ignore] pam_fpal.so` in front of `pam_unix.so`: a matching finger skips the password, anything else falls through to it. To go back, `sudo fpal setup --revert` (which runs `pam-auth-update --remove fpal`) restores `common-auth` as it was.

This is checked in a Debian and an Ubuntu container (`scripts/platform-container.sh`): enabling, enabling twice and removing leave `common-auth` exactly as expected. It has **not** been tried on a real Debian or Ubuntu machine with a sensor, nor with the GDM fingerprint screen there.

## Other systems

If neither `authselect` nor `pam-auth-update` is found (Arch, openSUSE, ...), `fpal setup` changes nothing and prints what to do by hand: the one `auth sufficient pam_fpal.so` line for the PAM services you choose, and the `fprintd` and `fpald` service commands.

## Options of `fpal setup`

| Option | Meaning |
|---|---|
| `--revert` | undo what `fpal setup` did |
| `--dry-run` | print every step and change nothing (needs no root) |
| `--backend NAME` | `authselect`, `pam-auth-update` or `manual`; by default the one this system has |
| `--no-services` | leave `fprintd` and `fpald` alone |

The GNOME login and lock screens first ask `net.reactivated.Fprint` over D-Bus whether a reader exists. `fpald` answers that, and the same script starts it; see [gnome.md](gnome.md).
